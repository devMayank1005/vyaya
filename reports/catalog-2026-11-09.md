# Findings: categories and accounts (Settings lists, account on an entry): 2026-11-09

**Scope:** `63d1a59`, which covers:
- `CatalogStore` (core/data);
- `CatalogScreen` (the lists and the category and account forms);
- account chips on Add entry;
- Settings → Your lists.

**Method:**
- Code analysis.
- Three temporary probes (not committed): long or blank names through the store, re-adding a deleted name, and 10,001
  categories followed by an export.
- The full local gate is green: jvmTest (simulations at default size), koverVerify, the shared and Android tests.

**Status:** reported only. **Nothing fixed.**

## Findings

1. **[DATA-001] [Medium] Changing an account's type or last digits is silently lost**
   - Where: `AccountForm` lets you edit the type and the last digits of an existing account. `VyayaRoot` calls
     `CatalogStore.renameAccount(a, name, …)`, which only changes the name.
   - How to reproduce: Settings → Accounts → HDFC ·1234 → change the last digits to 5678 → Save.
   - What happens: the form closes as if it saved, but the account is still ·1234.
   - Why it matters: the user thinks the change was saved. Later, when captured payments are matched by these
     digits (#4), it would be the wrong account.
   - Direction (not a fix): an `updateAccount(name, kind, mask)` that applies all three, or make those fields
     read-only for an existing account.

2. **[DATA-002] [Medium] Adding the 10,001st category or account makes every backup fail**
   - Where: `CatalogStore.addCategory` / `addAccount` have no limit. `BackupLimits.maxRecordsPerType` (10,000) is
     checked only when exporting.
   - How to reproduce (probe): with 10,000 categories, `addCategory` succeeds (0.19 s). Then `BackupStore.export`
     returns `Failure("Too many categories to back up: 10001 (limit 10000)")`.
   - Why it matters: no normal user gets there by hand. A restore can bring in up to 10,000, though, and one more
     added in the app then breaks every backup with no hint in the place where it was added. That breaks the "never
     write a backup you can't restore" promise from the other side.
   - Direction: the store refuses an add at the limit with a clear message ("You have 10,000 categories; delete
     some first"). Deleted records count too, because they are still backed up.

3. **[FLAW-003] [Medium] Re-adding a deleted name makes a second category with the same name**
   - Where: `addCategory` checks duplicates only among categories that aren't deleted.
   - How to reproduce (probe): add "Food", delete it, add "Food" again. That gives a new id, and `allCategories` has
     two "Food".
   - What happens: old entries stay on the deleted "Food" and new ones go on the new one. Any per-category total
     (budgets and reports in Phase 3, CSV) shows Food split in two. Nothing in the app lets you bring the old one
     back.
   - Direction: re-adding a deleted name restores that category (`deleted = false`), keeping its id.

4. **[FLAW-004] [Medium] Captured payments are never linked to an account**
   - Where: the parser extracts the masked digits (`Extractors`, `XX1234` → `1234`). Capture (`core/dedup`) doesn't
     match them to an `Account.mask`, so detected entries have no account. Recurring rules have an `accountId`, but
     the rule form can't set it.
   - Why it matters: accounts are useful only for entries added by hand. Most entries in Vyaya are captured, so
     "how much went through HDFC" can't be answered.
   - Direction: in capture, link an entry to the one account whose mask matches; if two accounts share digits,
     leave it unset. Let the rule form choose an account.

5. **[FLAW-005] [Low] Delete has no confirmation and no undo**
   - Where: the Delete buttons on the category and account forms. One tap deletes, and the item vanishes from the
     list.
   - Why it matters: it's easy to delete "Food" by mistake. Combined with #3, re-adding it splits the category.
     The data is still there (soft delete), but nothing in the app can bring it back.
   - Direction: a confirmation that says how many entries use it, or an Undo snackbar.

6. **[FLAW-006] [Low] An entry in a deleted category hides its category when edited**
   - Where: `AddEntryScreen` shows `categories.filter { !it.deleted }`. Accounts keep the entry's own deleted
     account visible (`|| it.id == accountId`), but categories don't.
   - What happens: editing such an entry shows no category selected. Saving keeps the old category anyway, so the
     user sees one thing and gets another.
   - Direction: show the entry's own deleted category as a chip (marked "deleted"), the same as accounts.

7. **[FLAW-007] [Low] A deleted category stays on rules and on future captures**
   - Where: recurring rules (and, from step 7, merchant memory) keep their `categoryId` after the category is
     deleted.
   - What happens: each month's generated entry goes into a category the user removed and can no longer choose.
   - Direction: when the category being deleted is used by rules, say so ("2 recurring rules use Food"), and move
     them or leave them.

8. **[PEN-008] [Low] The store throws on a name the model refuses**
   - Where: `renameCategory` / `renameAccount` pass the name straight to `copy`. A blank name or one over 100
     characters throws `IllegalArgumentException` (probe). `add*` returns null instead.
   - Reachable? Not from the UI today: the form refuses blank names and cuts at 100. But the call runs in
     `scope.launch`, so any future caller that skips the form's checks (a widget, a Shortcut, an import) would
     crash the app.
   - Direction: rename returns null or false like add does.

9. **[FLAW-009] [Low] Saving a too-long or odd name closes the form without saving**
   - Where: the form checks blank and duplicate names. When the model then refuses a name (`addCategory` returns
     null), `VyayaRoot` has already answered "saved" and closed the form.
   - Reachable cases are rare (the field already cuts at 100), but the pattern of "the form decides, the store
     disagrees silently" is the same as #1.
   - Direction: let the store's answer decide what the form says.

10. **[SEC-010] [Info] Names are free text and will reach the CSV export (step 6)**
    - Category and account names can be `=HYPERLINK(...)`, right-to-left overrides, or lookalikes (Cyrillic "Fооd"
      next to "Food"). In the app they are only shown as text, which is safe.
    - Direction: step 6 must pass names through `CsvExport.cell` (the formula guard) like payees. Lookalikes are
      accepted, by choice.

11. **[Info] People screen: the balance shows before the entry list**
    - The person's balance comes from the People list, and their entries load separately, so for one frame
      "Rahul owes you ₹200" shows over an empty list. This made a UI test flaky (fixed in the test by waiting for
      the entry). A user may see a brief flash.
    - Direction: load the balance and the entries together for the open person.

12. **[Info] Things that held up**
    - Duplicate names (any case, surrounding spaces) are refused for the same type; "Pets" as spending and as
      income are both allowed.
    - Rename and delete apply to the record as it is now (by id), so a stale screen can't undo an earlier change.
    - A deleted account stays visible and selected on an entry that already uses it.
    - The last-digits field accepts only digits (3–6), and the model checks again.
    - Deleted categories still name old entries on Home.
    - The simulation harness doesn't cover this feature directly: it doesn't touch parsing, de-dup, the engine or the
      backup format. The default-size simulations ran green in jvmTest. The records path is covered by the backup
      round-trip simulation.

## Decisions needed from you
- **#1:** apply type and last digits on edit (recommended), or make them read-only?
- **#2:** refuse adds at the 10,000 limit (recommended)?
- **#3:** re-adding a deleted name brings the old one back (recommended)?
- **#4:** link captured payments to an account by its last digits (recommended; it fits with step 7, merchant
  memory)?
- **#5–#9:** confirm on delete with the number of uses; show a deleted category on its own entries; warn about
  rules; rename returns false; the store's answer decides the form message (all recommended).
