## Findings

1. **[DATA-001] [High] Exporting from the database can write a backup that restore refuses**
   - Where: `BackupStore.export`. It copies row lines as they are and skips `Consistency.problems`, the check that
     `BackupCodec.write` runs before writing (DATA-001 of an earlier report: never write a backup you can't restore).
   - How to reproduce (probe): edit an entry while the phone's clock is ahead (`updatedAt` 4 Nov). The clock is
     corrected, then the user exports (3 Nov). `BackupCodec.write` refuses ("changed after the backup was made").
     `BackupStore.export` returns **Success**, and restoring that file is **Refused** with the same problem.
     "Restore anyway" doesn't help (it only handles a backup newer than the phone).
   - Why it matters: the user finds out only when restoring, often on a new phone after losing the old one.
     `ClockRepair` would have repaired this, but it isn't wired to the database (see #4).
   - Direction: while exporting, run the lines through a `BackupDecoder` (streaming, cheap) and fail the export
     with its problems. Or run the same checks on the rows before writing.

2. **[PEN-002] [Medium] A crafted file of many small non-entry records runs restore out of memory**
   - Where: `Reader` (core/backup). Only entries are streamed; accounts, categories, people, rules, ledger, budgets
     and merchant rules are kept in memory until the end.
   - How to reproduce (probe): an 89 MB file with 500,000 merchant rules, within every current limit, restored with
     a 256 MB heap gives **OutOfMemoryError** after 4.6 s.
   - What happens: on a phone the app crashes. The database is safe (the transaction is never committed).
   - Why it matters: a file shared as "my backup" can crash the app every time it's chosen. No real user has more
     than a few hundred of these records.
   - Direction: a per-type limit for non-entry records (e.g. 10,000 each), checked by writer and reader alike
     (rule 8.7: easy now, before the first release). Or stream every record type the way entries are.

3. **[DATA-003] [Medium] A Replace restore leaves the Detected inbox untouched**
   - Where: `BackupStore.restore` clears `records` and `entries` but not `detected`.
   - What happens (by analysis):
     - Open items still list payments from before the restore.
     - "Undo" on an ADDED item soft-deletes a restored entry that has the same id (or does nothing).
     - "Confirm" on a REVIEW item adds an entry captured before the restore, which may be one the backup already has.
   - Direction: Replace closes (or clears) the open inbox items in the same transaction. Merge can keep them.

4. **[FLAW-004] [Medium] App start and clock repair still need the whole snapshot in memory**
   - Where: `SnapshotStore.load()`. `ClockRepair` and the engine work on a `Snapshot`, so at 200,000 entries the
     app would load them all (~470 MB in the codec measure) just to open.
   - Why it matters: export and restore are now streamed, but the app's own open isn't. It's also why #1 can
     happen: nothing runs `ClockRepair` on the database.
   - Direction: run clock repair and recurring catch-up as database queries (future-month generated entries and
     change times after now, by their columns). Screens read by month.

5. **[FLAW-005] [Medium] A restore holds the database's write lock for as long as the file takes to read**
   - Where: `BackupStore.restore`. The whole file is read inside one write transaction (that's what makes it all or
     nothing).
   - What happens: 200,000 entries take 5.8 s on a Mac, likely 20–60 s on a low-end phone, longer if the file
     streams from a slow cloud provider. Captures arriving meanwhile wait (the notification listener blocks).
   - Direction: copy the file to app storage first (fast, no lock), then restore from the local copy, with a
     progress screen. Captures wait or queue, with a time limit.

6. **[DATA-006] [Low] One damaged row makes the whole database unreadable**
   - Where: `SnapshotStore.load` throws on a row that doesn't read back.
   - How (by analysis): a row edited outside the app (rooted phone, a database copied in by hand) or a storage fault.
   - What happens: every app start crashes. Meanwhile export copies the bad line into the backup (see #1), and
     the key columns (`amountPaise`, `occurredAtMs`, `deleted`) can differ from the line without anything noticing.
   - Direction: on a bad row, open in a "repair" state that lists the damaged rows, can export the rest, and
     offers restoring the last good backup.

7. **[SEC-007] [Medium, for the Android step] The database is plain SQLite on disk**
   - What: rows hold payees, notes, UPI references and amounts. On Android, Auto Backup copies app data to Google
     Drive unless excluded. Plan rule 8.8: nothing leaves the device.
   - Direction (Android step): exclude the database from Auto Backup and device transfer (`dataExtractionRules`).
     Decide about at-rest encryption (SQLCipher, or Android Keystore for backups only).

8. **[FLAW-008] [Low] A read error part-way through a restore escapes as an exception**
   - Where: `restore(lines, …)`. An `IOException` from the file (a download cut off, a cloud provider error) is not
     a `Refused` result. The transaction rolls back, but the caller gets a raw exception.
   - Direction: catch read errors and return `Refused("The file couldn't be read to the end")`.

9. **[Info] Export pages with LIMIT/OFFSET**
   - 200,000 entries: 1.3 s, fine. OFFSET rescans earlier rows, so the cost grows as n². Keyset pages
     (`WHERE id > :last`) would keep it linear if records grow much larger.

10. **[Info] Things that held up**
    - All or nothing: 10,000 damaged files never left a partly restored database, including damage found only at
      the end (checksum) after batches were written.
    - Merge compares the exact `updatedAt` from the line, not the millisecond column.
    - Duplicate entry ids split across batches are caught by the end check and rolled back.
    - Export runs in one read transaction, so a capture arriving mid-export is either all in the file or not at all.
    - v1 and v2 files restore into the database.
    - The Detected inbox stores no SMS text (only the entry line and a hash id).
