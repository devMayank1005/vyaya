## Findings

1. **[SEC-001] [Medium] The iOS database uses the default file protection**
   - What: iOS encrypts app files, but by default ("until first user authentication") the file stays readable while
     the phone is locked, once it was unlocked after a restart.
   - Direction: `FileProtectionType.complete` on the database folder. The app does no background work on iOS, so it
     never needs the file while the phone is locked.

2. **[FLAW-002] [Medium] Backups don't work on iPhone yet**
   - The Backup tab says "Backups on iPhone come in the next update". Until then, an iPhone user can't move data or
     keep a copy. This is stage 3.
   - Direction (for your agreement): the `.vyaya` chunk format moves into shared Kotlin, so one implementation serves
     both apps. Then:
     - iOS supplies AES-GCM from CryptoKit through a tiny Swift class, tested against NIST GCM vectors;
     - PBKDF2 comes from CommonCrypto (`CCKeyDerivationPBKDF`, public);
     - the spec's vectors run on both platforms;
     - files go through the system's file picker.

3. **[Info] Not yet run on an iPhone:** Face ID, the passcode fallback, and the blank app-switcher screen need a
   device. To try it: open `iosApp/iosApp.xcodeproj` in Xcode, choose your team under Signing, and run on your iPhone.

4. **[Info] Things that held up**
   - The database is in Application Support, in a folder excluded from iCloud and computer backups (tested).
   - It reopens from its file with the data intact; the open routine (categories, clock repair, catch-up) runs on iOS.
   - The lock follows the same shared rules as Android: 30 seconds, a fresh start locks, turning it on or off asks.
   - The passphrase uses the system's secure random (`SecRandomCopyBytes`), tested on the simulator.
   - No Detected tab on iOS (no access to notifications or SMS there; Shortcuts and screenshots come later in the plan).
   - Every Android test still passes on the shared screens; CI builds the iOS app.
