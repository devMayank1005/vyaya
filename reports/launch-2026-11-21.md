## Findings

1. **[FLAW-001] [Medium] The minified build is checked only for opening screens**
   - Where: `release-smoke.sh` covers Home, Add, the widget's redraw and the tile. None of these runs in the minified
     build:
     - exporting and restoring a backup (kotlinx.serialization, AES-GCM, the file pickers);
     - the CSV export;
     - the app lock (biometric prompt);
     - capture from a notification;
     - budget alerts.
     R8 failures show up only at run time, on users' phones. The smoke test also isn't in CI.
   - Why it matters: a stripped or renamed class in the backup or lock paths would ship unnoticed. Those are the
     paths where a failure costs data or access.
   - Direction: run a set of the existing tests against the minified build: AGP's `testBuildType` for instrumented
     tests on a minified variant, or Robolectric over the R8 output. Run the smoke test in CI on an emulator runner,
     at least before a release tag.

2. **[PEN-001] [Low] Any app can stack more copies of Vyaya's screen**
   - Where: `MainActivity` has the default launch mode. An intent without `SINGLE_TOP` (another app's, or `am start`
     as the smoke test first did) opens a second instance on top. The emulator showed two in one task.
   - What happens: each copy has its own screen state and reads the database. Back from the top copy shows the older
     one. The app lock is per process, so it still asks, and each window gets `FLAG_SECURE`. Nothing leaks; it's a
     confusing back stack and double work.
   - Direction: `android:launchMode="singleTop"` (the widget and tile already ask for it), or `singleTask`.

3. **[FLAW-002] [Low] A lost `mapping.txt` makes a release's crash reports unreadable**
   - Where: releases are built on your machine with your key. The mapping for each `versionCode` exists only in your
     local `build/` folder until you upload it with the `.aab`.
   - Direction: the checklist already says to upload it. Also keep a copy per version (for example, a
     `release-mappings/<versionCode>.txt` outside the repository, or a CI job that builds the `.aab`).

4. **[SEC-001] [Low] The setup card's explanation may be thin for Play's notification-access review**
   - Where: "Vyaya reads payment notifications from UPI and bank apps on this phone. Nothing leaves the phone." Play
     reviews apps that use notification access for what they read and why. Its User Data policy asks for a prominent
     disclosure before access, when the use isn't obvious.
   - Direction: before the button, list what is read (the amount, payee and time from listed payment apps) and what
     isn't (other apps' notifications are dropped unread; message text isn't kept). Use the same words in the store
     listing.

5. **[Info] Still open from earlier reports and the checklist**
   - The launcher icon is a placeholder.
   - The database isn't encrypted at rest (core-data SEC-008, waiting on your decision). The private app storage
     and the phone's own encryption protect it.
   - New Play personal accounts need a 12-tester, 14-day closed test before production.
   - `biometric` 1.1.0 is the newest stable release but dates from 2021. No known issue was checked online (see
     Method).
   - The full (SMS) build is side-load only. Play allows SMS permissions only for default SMS apps.

6. **[Info] Things that held up**
   - The upload key and its passwords are read only from your `~/.gradle/gradle.properties` or the command line.
     Without them, release builds stay unsigned, which is what CI builds. Verified both ways.
   - On Android 17 (the emulator), `APPWIDGET_UPDATE` is a protected broadcast: even the shell can't send it. Widget
     report PEN-001 (other apps making the widget redraw) can't happen there; the coalescing stays for older
     versions.
   - The committed database schema must match what Room compiles (a CI step), ready for "migrations from the first
     beta".
